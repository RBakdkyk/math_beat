## Context

Greenfield Python project. No existing codebase. The user's daughter needs daily math practice aligned to the Israeli 4th grade curriculum (kita4). The system generates questions via a deterministic template engine (most question types) with Claude CLI fallback (word problems only), tracks progress via structured JSON files, and outputs WhatsApp-ready Hebrew text.

The wiki pattern (lean JSON files, date-stamped sessions) is borrowed from the user's existing `autoresearch-ta` project.

## Goals / Non-Goals

**Goals:**
- Generate curriculum-aligned Hebrew math questions with variance — deterministically where possible
- Minimize token usage: ~75% of questions generated by Python template engine, zero tokens
- Track per-topic/subtopic progress with individual item tracking (correct/wrong counts, used parameters)
- Multiplication table tracked as 55 individual facts with per-fact correct/wrong history
- Signature-based deduplication: avoid repeating the same mathematical content recently
- Adapt to weakness: wrong answers → similar parameters next time; right answers → new parameters
- WhatsApp-ready output (copy-paste, no special formatting)
- Simple CLI interface: `generate.py` and `analyze.py`
- First 2-3 sessions work without prior state (bootstrapping/diagnostic mode)

**Non-Goals:**
- Web UI or app
- Automated WhatsApp integration
- Automated grading / answer checking
- Multiple children / user management
- Non-math subjects (document is math-only)
- Anthropic API key management

## Decisions

### 1. Template engine over Claude CLI for most question types
**Choice:** Python template engine generates ~75% of questions deterministically. Claude CLI only called for word problems, geometry descriptions, and data/probability scenarios.
**Why:** Token efficiency. Multiplication drills, basic arithmetic, fraction computation, order of operations, divisibility, and prime/composite questions are structurally predictable — a template + random numbers within curriculum constraints produces equivalent quality to LLM generation. At 5-10 questions/day, this eliminates most token costs.
**Alternative:** Claude CLI for everything — simpler code but wasteful when most questions are "compute {a} {op} {b}".

**What Python generates (zero tokens):**
- Multiplication table drills (55 facts × multiple templates)
- Basic arithmetic (add/subtract/multiply/divide with multi-digit numbers)
- Fraction computation and comparison (constrained denominator pairs)
- Order of operations expressions
- Divisibility rule questions
- Prime/composite identification

**What needs Claude (tokens):**
- Word problems (creative Hebrew story context)
- Geometry questions with spatial descriptions
- Data/probability scenarios
- Estimation/number sense with natural phrasing

### 2. Curriculum knowledge from CandleKeep PDF
**Choice:** Use CandleKeep to read the full kita4 PDF and extract structured curriculum knowledge into `src/curriculum_knowledge.md`. CLAUDE.md points to this file so every Claude Code session and the generation skill always have the curriculum grounded from the source document.
**Why:** The PDF is the authoritative source. Extracting once via CandleKeep and persisting as a project file means generation prompts always reference the actual curriculum — not a hand-summarized approximation. The CLAUDE.md pointer ensures any Claude Code session in this project has the context without re-reading the PDF.
**Alternative:** Re-read the PDF via CandleKeep on every generation run — wasteful and slow for a static document.

### 3. Rule-based difficulty tiers, not enumerated pools
**Choice:** Each subtopic defines difficulty levels (easy/medium/hard) as number range constraints and validation rules, not as exhaustive lists of parameter combinations. Python generates valid numbers at runtime from these rules.
```python
"fraction-addition": {
    "easy":   { "max_denom": 6,  "unit_fractions": True },
    "medium": { "max_denom": 10, "max_numerator": 5 },
    "hard":   { "max_denom": 12, "max_numerator": 11 },
    "constraint": "denom2 % denom1 == 0"
}
```
**Why:** Enumerated pools are finite and require manual maintenance. Rules generate an effectively infinite pool — the constraint function validates each combination at generation time. Difficulty scales naturally by widening/narrowing the ranges.
**Alternative:** Explicit lists of valid parameter tuples — works for small pools (multiplication facts) but doesn't scale for arithmetic, fractions, or division where the space is large.

### 4. Topic tree as a Python module
**Choice:** `curriculum.py` defines the topic tree as Python dicts with rule-based constraints co-located.
**Why:** The tree is static (seeded from kita4). Python code can embed constraint functions alongside the data. A separate JSON config adds indirection with no benefit for a single-user tool.
**Alternative:** Separate JSON config per subtopic — more files, more indirection, unnecessary.

### 5. Session composition from progress, no "current topic" config
**Choice:** Weighted selection based on three signals from summary.json:
1. `correct_rate` — lower rate → more questions
2. `last_practiced` — longer ago → higher priority
3. `times_practiced` — fewer times → higher priority (new topics get explored)

Fixed structure per session:
- 3 warmup questions (multiplication, targeting weakest facts)
- Remaining questions split between weakest and second-weakest topics

All topics from kita4 are available. No "current school topic" configuration — the progress data drives what gets practiced. Untouched topics (times_practiced: 0) naturally surface through the priority algorithm.

**Why:** Simple, transparent, self-adapting, and easy to override via CLI args when the parent wants to force a topic.

### 6. Structured summary.json with item-level tracking
**Choice:** summary.json tracks per-topic AND per-item state:
```json
{
  "topics": {
    "multiplication-table": {
      "correct_rate": 0.58,
      "times_practiced": 12,
      "last_practiced": "2026-05-07",
      "facts": {
        "7×8": { "correct": 2, "wrong": 3, "last_seen": "2026-05-07" },
        "6×7": { "correct": 1, "wrong": 2, "last_seen": "2026-05-06" }
      }
    },
    "fraction-addition": {
      "correct_rate": 0.40,
      "times_practiced": 3,
      "last_practiced": "2026-05-06",
      "used_params": [
        { "sig": "1/2+1/4", "date": "2026-05-06", "correct": false },
        { "sig": "1/3+1/6", "date": "2026-05-05", "correct": true }
      ]
    }
  }
}
```
**Why:** Python needs to know not just "fractions are weak" but specifically which parameter combinations were used, when, and whether she got them right. This drives the generation logic:
- Wrong answers → generate similar parameters next time (same denominator family, nearby numbers)
- Right answers → new parameters, expand coverage
- Items older than 5 sessions → eligible for reuse

### 7. Signature-based deduplication
**Choice:** Each generated question gets a mathematical signature (e.g., `"mult:7×8"`, `"fraction-add:1/2+1/4"`, `"divide:524÷4"`). The generator checks recent signatures in summary.json's `used_params` and rejects collisions.
**Why:** Deterministic, fast (set lookup), no tokens. The signature captures the math content, not the phrasing — so the same numbers with a different Hebrew template would still be rejected. If the generator can't find a non-duplicate after N attempts, falls back to Claude for that question.
For Claude-generated word problems, signatures follow the pattern `wordproblem:{category}:{level}` — the story context varies but the mathematical category and difficulty are tracked.

### 8. Wiki file layout
```
wiki/
  sessions/
    2026-05-08/
      generated.json    # output of generate.py
      results.json      # parent fills (or LLM-assisted)
  progress/
    summary.json        # structured state — the system's memory
```
**Why:** Date-stamped directories are human-browsable and git-friendly. `summary.json` is the single source of truth for the generator — rebuildable from session history if needed.

### 9. Overwrite protection
**Choice:** If `generated.json` already exists for a date, `generate.py` refuses and prints a warning. Same for `results.json` via `/results`. Use `--force` to overwrite.
**Why:** Accidental double-runs shouldn't silently lose data.

### 10. used_params 15-day retention prune
**Choice:** When `analyze.py` updates summary.json, it prunes `used_params` entries older than 15 days. Multiplication `facts` are never pruned (they're cumulative counts, not event logs).
**Why:** After 15 days, parameter combinations are eligible for reuse anyway. Unbounded growth would slow lookups and bloat the file over months.

### 11. Results via Claude Code skill, not manual JSON editing
**Choice:** A `/results` skill provides a guided conversational flow for entering session results. Parent reports what the child answered per question in natural language. The skill reads `generated.json` (knows correct answers), determines correctness, asks for clarification if ambiguous, then writes `results.json` and runs `analyze.py` to update `summary.json`.
**Why:** The parent shouldn't have to manually write JSON or remember question IDs. The skill already knows the questions and answers — the parent just relays what the child said. "She said 54" is enough when the skill knows the answer is 56. "Didn't understand" is marked as wrong with a note (valuable signal for the generator to adjust difficulty).
**Flow:**
1. Parent runs `/results` in Claude Code
2. Skill loads today's `generated.json`
3. Parent describes child's answers naturally ("q1 she said 56, q2 she got wrong wrote 42...")
4. Skill matches to questions, determines correct/wrong, asks if unclear ("what did she answer for q6?")
5. Skill writes `results.json`, runs `analyze.py`, shows progress summary
**Alternative:** Manual `results.json` editing + `python analyze.py` — works but friction kills daily habits.

## Risks / Trade-offs

**Template variety fatigue** → With limited templates per subtopic, phrasing may feel repetitive. Mitigation: start with 3-5 templates per type, expand over time. The mathematical content varies even if phrasing is similar.

**Hebrew RTL in terminal** → Terminal may not render Hebrew well. Mitigation: the primary output is WhatsApp (copy-paste), terminal display is secondary.

**Cold start accuracy** → First sessions have no progress data, so topic selection is generic. Mitigation: explicit bootstrapping mode that covers broad topics at easy difficulty, treating early sessions as diagnostic.

**Single summary.json corruption** → If the file gets corrupted, all progress is lost. Mitigation: summary.json is rebuildable from session history (generated.json + results.json are the source of truth). Add a `rebuild-progress` command.

**Parameter pool exhaustion** → Some subtopics have small valid parameter pools (e.g., "close" denominator pairs). Mitigation: fall back to Claude CLI for that question when pool is exhausted after N attempts.
